# Контракт потребителя

[English](consumer-variables.md) | [Русский](consumer-variables.ru.md)

Continuum настраивается **вызывающим репозиторием**. Общие движки не несут
значений по умолчанию, скопированных из какого-либо существующего потребителя.

> [!NOTE]
> Входы переиспользуемого workflow имеют приоритет над переменными
> репозитория. В движке валидации пустой вход означает переход к соответствующей
> переменной репозитория `CONTINUUM_*`; в агентском пути
> `CONTINUUM_OPENCODE_VERSION` переопределяет проверенный манифест действия,
> только когда задан точным SemVer.

## Валидация

`continuum-validation.yml` — общий движок валидации. Любая настройка может быть
передана входом переиспользуемого workflow; пустой вход означает переход к
переменной репозитория, указанной ниже.

| --- | --- | --- |

### Допуск пробуждения CI-ремонта

GitHub не позволяет использовать переменную репозитория в фильтре события
`workflow_run`, поэтому установленный вызыватель ремонта всё равно создаёт
запуск контроллера для каждого завершённого workflow. Поэтому вызыватель и
переиспользуемый контроллер читают `CONTINUUM_CI_REPAIR_WORKFLOWS` в своём
`if` уровня задачи и пропускают раннер до любого checkout, git fetch или вызова
GitHub API, когда завершённое имя не может быть допущено. Проверка —
консервативный подстрочный супернабор точного allow-list контроллера с учётом
запятых и переводов строк, поэтому она никогда не пропустит одобренное имя, а
точный runtime-допуск остаётся авторитетным.

Подавленное завершение получает уникальную concurrency-группу, поэтому оно не
может заменить ожидающий запуск того же HEAD для одобренного workflow. Все
одобренные имена workflows, включая пользовательские имена, добавленные в
переменную позже, по-прежнему используют блокировку exact-HEAD. Прямой отчёт CI
через `workflow_dispatch` и путь синхронизации ветки `pull_request_target` этот
допуск по имени не используют и не затронуты.

Это изменение не убирает широкий триггер `workflow_run` и не вводит таймер;
само создание запусков workflow остаётся ограничением GitHub, а устойчивый
приём/вывод всех событий остаётся за приостановленной последующей работой
#344/#345.

Обновление: переустановите набор `core`, чтобы установленный вызыватель тоже
пропускал работу до создания переиспользуемой задачи. Существующие
установленные вызыватели уже получают преимущество runtime-допуска
контроллера, потому что он подключается на `@main`. Откат: восстановите
предыдущую ревизию вызывателя и/или контроллера `continuum-opencode-repair.yml`;
триггер события и оба независимых пути диспетчеризации не меняются, поэтому для
отката миграция триггера не нужна.

Режим задачи использует тот же контракт проверки, авторитетный для репозитория.
Перед основной сессией кодирования он разрешает литеральные значения
`prepare_command`, `build_command`, `test_command` и `validation_command`
потребителя из основного вызывателя `CI` (файла, который вызывает
`continuum-validation.yml`), с запасным вариантом в виде соответствующих
переменных репозитория `CONTINUUM_*_COMMAND`. Должна разрешиться хотя бы одна из
build, test или validation; иначе реализация fail-closed завершается явным
несконфигурированным состоянием, а не изобретает проверку под конкретный стек.
Не-литеральное выражение GitHub, отличное от `${{ vars.NAME }}`, также является
явным несконфигурированным сбоем и никогда не тихим запасным вариантом на другую
команду.

Разрешённый набор команд выполняется один раз перед реализацией, чтобы записать
базовую линию, затем снова после свежей независимой сессии OpenCode
verifier/fix. Финальный запуск использует точные команды базовой линии и
отпечаток окружения. Неудачная или недоступная проверка после изменений никогда
не даёт успешный результат; уже существовавший сбой базовой линии записывается
отдельно и не становится зелёным. Свидетельство `.continuum-verification.json`,
принадлежащее workflow, сохраняется при checkpoint 429 и удаляется перед
коммитом/PR реализации.

Файл свидетельства живёт в рабочем дереве задачи, поэтому движок никогда не
доверяет ему сам по себе. Движок проверки распознаёт необязательный внутренний
хук аттестации HMAC-SHA256, только когда его окружение процесса предоставляет
путь `CONTINUUM_VERIFICATION_ATTESTATION_KEY_FILE` к приватному файлу ключа вне
рабочего дерева задачи. Само значение ключа никогда не читается из окружения:
управляемая репозиторием команда может просмотреть унаследованное окружение
движка через `/proc/$PPID/environ`, поэтому установка
`CONTINUUM_VERIFICATION_ATTESTATION_KEY` в окружении движка завершается
fail-closed, а не принимается. Движок читает файл ключа в каждом процессе CLI
проверки и никогда не передаёт значение ключа или путь к его файлу управляемой
репозиторием команде. Каждый вызов, который читает ключ (`baseline`,
`needs-verifier`, `record-verifier`, `final`, `summary`), читает его в память и
сразу удаляет копию на диске — настроенный путь и его разрешённую цель symlink —
поэтому после любого такого вызова файла ключа не остаётся. Копия никогда не
записывается обратно: команда может породить процесс того же uid, который
переживёт движок и прочитает любой файл, доступный движку, поэтому
восстановление файла в конце команды или процесса либо оставление его после
прерывания передало бы ключ этому процессу. Последующий вызов, которому нужен
ключ, должен явно подготовить его заново из авторитетного источника, например
`printf '%s' "$KEY" | python -m continuum.verification provision-key --repo "$GITHUB_WORKSPACE"`,
который читает ключ из стандартного ввода (никогда из аргумента или окружения),
пишет атомарно с режимом `0600` и отказывается заменять другой ключ. Workflow
должен заново готовить ключ перед каждым вызовом CLI проверки, которому он
нужен, и никогда не готовить его во время агентской сессии: агент работает с
теми же правами пользователя в той же задаче и мог бы прочитать файл и
подписать подделанную запись `verifier` или `final`, которую возобновлённый
запуск `tests-passed` или `publish-pr` принял бы при верной HMAC. Если файл
отсутствует, когда нужен, или копию на диске нельзя удалить после чтения,
движок fail-closed завершается явным `::error::`, а не продолжает без
аттестации. Поставляемый workflow `continuum-opencode.yml` объявляет
необязательный секрет `CONTINUUM_VERIFICATION_ATTESTATION_KEY` и, когда
потребитель его задаёт, готовит приватный файл ключа непосредственно перед
каждым вызовом CLI проверки. Поэтому это необязательный секрет потребителя, а
не скрытая внутренняя настройка: не задавать его полностью поддерживается и
отключает аттестацию (возобновлённый запуск тогда пересобирает и заново
разрешает контракт вместо доверия записанным свидетельствам), и тогда workflow
вообще не экспортирует `CONTINUUM_VERIFICATION_ATTESTATION_KEY_FILE`. Когда
ключ задан, он используется только локальным для раннера верификатором и
никогда не раскрывается агентским командам или командам проверки потребителя.
Если задан, он подписывает записанные контракт, базовую линию, результат
верификатора и принятую финальную запись, а возобновлённый запуск использует эти
записи, только когда подпись верна. Без ключа существующая базовая линия никогда
не считается доверенной. Если возобновлённый checkout ушёл вперёд от базы
задачи, проверка fail-closed требует свежий checkout на этой базе; запись
рабочего дерева без аттестации никогда не принимается как свидетельство. Ключ
читается из приватного файла, никогда из аргумента или окружения, поэтому он не
появляется в списках процессов.

Переиспользуемый движок **не** устанавливается как вызыватель
`continuum-validation.yml`. Каждый потребитель владеет одним основным
`.github/workflows/ci.yml`, чьё имя workflow — **CI**, и вызывает
`kodmial/continuum/.github/workflows/continuum-validation.yml@main`. Это
сохраняет различия триггеров и toolchain проектными, не создавая второй общий
конечный автомат CI. Core-логика ремонта/watchdog рассматривает стабильное имя
workflow `CI` как интерфейс, а `CONTINUUM_CI_REPAIR_WORKFLOWS` расширяет этот
интерфейс только дополнительными точными именами workflows, которые потребитель
явно одобрил (например, workflow продуктовых тестов с именем `Windows host`).
Блокировка ремонта разделяется между этими workflows для каждого HEAD PR,
поэтому один зелёный workflow никогда не снимает блокировку, которая всё ещё
нужна другому одобренному workflow.

## Выполнение агента

| Переменная репозитория | По умолчанию | Значение |
| --- | --- | --- |
| `AUTOMATION_OPENCODE_RUNNER` | `ubuntu-latest` | Раннер, используемый OpenCode. |
| `AUTOMATION_OPENCODE_TIMEOUT_MINUTES` | `180` | Таймаут OpenCode. |
| `CONTINUUM_AGENT_PREPARE_COMMAND` | пусто | Настройка toolchain/окружения потребителя, выполняемая после checkout. |
| `CONTINUUM_OPENCODE_VERSION` | `2.2.6` (манифест действия по умолчанию) | Точное переопределение SemVer для общего bootstrap hosted-кэша OpenCode; невалидные или недоступные пины завершаются fail-closed, без подвижного `latest`. Переменная репозитория имеет приоритет, только когда задана точным SemVer; когда не задана, авторитетен `.github/actions/agent-toolchain/toolchain.json` (`2.2.6` на этой базовой линии). Используется задачей кодирования, ревью/ремонтом PR-Agent и делегированными агентскими задачами Child. PR-Agent отдельно проверяет digest своего закреплённого wheel. |
| `CONTINUUM_IMAGE_DIGEST` | пусто | **Устаревший digest нативного образа/профиля, сохранён для совместимости** с переиспользуемыми входами `image_digest` (они всё ещё передают `inputs.image_digest \|\| vars.CONTINUUM_IMAGE_DIGEST`). До Work Lock #67 Linux-задачи OpenCode на GitHub-hosted раннерах трактовали его как возможный штамп предустановленного runtime, а иначе запускали встроенный холодный установщик; на свежих hosted VM это был обманчивый прокси тёплого кэша. **После миграции #67** шесть активных workflows кодирования/ревью/ремонта/делегации на GitHub-hosted раннерах восстанавливают и проверяют бинарники OpenCode через `agent-toolchain` + `actions/cache`, поэтому установка этой переменной не может создать hosted-попадание в кэш. Потребители с реальным отдельно проверенным провайдером нативного golden-image всё ещё могут использовать digest как идентичность профиля; такие бэкенды и macOS/Windows не проверены hosted-cache тестами. Устаревшие входы вызывателя по-прежнему принимаются, но не должны трактоваться как пины hosted-кэша. |
| `CONTINUUM_RUNTIME_PRESET` | `agent-linux` | Именованный preset эфемерного runtime (`agent-linux`, `agent-macos`, `agent-windows`, ...). Строгие presets сохраняют `idle_instances: 0` и `max_uses_per_instance: 1`; их нельзя перенастроить в постоянные ожидающие раннеры. |
| `CONTINUUM_RUNTIME_PROVIDER` | `github-hosted` | Бэкенд провайдера для эфемерных экземпляров (`github-hosted`, `gce`, `ec2`, `azure`, `custom`). |
| `OPENCODE_MODELS` | пусто | Упорядоченный пул из 1–8 уникальных идентификаторов `provider/model` через запятую для failover-маршрутизации. Пусто отключает маршрутизацию пула; применяется запасной одномодельный `OPENCODE_MODEL`. Некорректные, дублирующиеся или лишние записи завершаются fail-closed. |
| `OPENCODE_MODEL_STRATEGY` | `sticky-failover` | Стратегия выбора из пула. `sticky-failover` — единственное поддерживаемое значение; любое другое завершается fail-closed. |
| `OPENCODE_PROBE_TTL` | `3600` | Секунды, в течение которых успешная проверка маршрута остаётся свежей. Целое в `[60, 86400]`. |
| `OPENCODE_MODEL_COOLDOWN` | `900` | Секунды, в течение которых сбойный или исчерпанный маршрут исключён из выбора. Целое в `[60, 86400]`. |
| `OPENCODE_PROBE_TIMEOUT` | `90` | Таймаут одной проверки в секундах. Целое в `[15, 240]`. |

`OPENCODE_MODEL` — только устаревший запасной вариант для одной модели: он
используется, когда `OPENCODE_MODELS` пуст. Явный пин на конкретный запуск
должен быть одним из маршрутов пула. Полный контракт выбора, квалификации и
состояния — во внутреннем документе `docs/opencode-model-routing.md` (на
английском).

Строгие эфемерные инварианты (ноль живых idle-экземпляров, одна задача на
экземпляр, сетевой жизненный цикл на задачу, teardown с поддержкой reconciler)
обеспечиваются путём провижининга Continuum (`src/continuum/agent_runtime.py`:
`resolve_profile` / `resolve_profile_from_env` плюс `EphemeralController` и
reconciler `sweep_orphans`) для строгих профилей, которые сохраняют
`idle_instances: 0` и `max_uses_per_instance: 1`; сами по себе переменные из
этого файла ничего не провижинят. GitHub-hosted раннеры и так являются свежими
экземплярами на каждую задачу; подготовленный runtime (golden image или его
эквивалент в виде content-addressed кэша) — это то, что делает их быстрыми.
Заранее созданного пула живых VM нет, и гарантии уникальности IP между задачами
нет.

В ядре нет неявной настройки macOS или языков.

## Необязательный профиль Swift

Набор `tech` устанавливает `continuum-tech-swift-ci.yml` — нейтральный к
продукту профиль над тем же движком валидации.

| Переменная репозитория | По умолчанию |
| --- | --- |
| `CONTINUUM_SWIFT_RUNNER` | `macos-latest` |
| `CONTINUUM_SWIFT_BUILD_COMMAND` | `swift build` |
| `CONTINUUM_SWIFT_TEST_COMMAND` | `swift test` |

Приложения, которым нужен конкретный образ macOS, выбирают его явно в своём
workflow или конфигурации. Подпись, манифесты пакетных менеджеров и публикация
релиза не входят в профиль Swift.

| `AUTOMATION_READY_LABEL` | пусто | Необязательная метка допуска для автоматической реализации. Когда задана (например, `automation:ready`), планировщик автоматически запускает только задачи с ней; пусто сохраняет текущее поведение. Запуск квалификации и ручная команда владельца `/oc` её не требуют. |
| `CONTINUUM_REVIEW_PROVIDER` | `none` | Авторитетный выбор ревью: `none`, `coderabbit` или `pr-agent`. |
| `CONTINUUM_CONTRACT_GATE_WORKFLOW_NAME` | `Continuum Contract Gate` | Имя workflow для Contract Gate при восстановлении владельцем. Гейт по exact-HEAD обязателен в каждом репозитории; эта переменная только переименовывает обязательный workflow. |
| `CONTINUUM_VERSION_FILE` | пусто | Необязательный путь к файлу версии внутри репозитория. Используется только общей служебной логикой: отмена устаревших запусков `Release` для уже опубликованной версии и распознавание PR релизной автоматизации при навешивании меток ревью. Пусто отключает эти оптимизации; это не включает release-автоматизацию. |

> [!IMPORTANT]
> `AUTOMATION_READY_LABEL` пуста по умолчанию. Пока она пуста, планировщик
> может поставить в очередь любую подходящую открытую задачу. Задайте её до
> открытия задач.

Устаревшие входы `workflow_call` `child_owned_marker` и
`legacy_child_owned_marker` всё ещё принимаются, чтобы старые вызыватели
продолжали работать, но маркеры в теле задачи больше не влияют на допуск
планировщиком. Проверенная маршрутизация детей использует `CONTINUUM_ROLE` и
переменные связей выше.

### Обязательный workflow Contract Gate

Восстановление владельцем авторизуется комментарием владельца через API, первая
строка которого — ровно маркер ниже (владелец может добавить объяснение после
него):

```html
<!-- continuum-resume-after:v1 predecessor=374 -->
```

`predecessor` — номер задачи, которая должна быть закрыта как выполненная с
доверенным слитым PR реализации. Ручная команда `/oc` в приостановленной задаче
— это команда OpenCode, а не этот маркер: она считается активностью, которая
ограничивает маркер, и не взводит переход.

HEAD PR-предшественника должен нести успешный запуск Contract Gate.
Планировщик сопоставляет этот запуск по `name:` workflow (или по пути
`.github/workflows/contract-gate.yml`) и по умолчанию использует имя
`Continuum Contract Gate`, когда `CONTINUUM_CONTRACT_GATE_WORKFLOW_NAME` не
задана или пуста. Поэтому потребитель должен предоставить workflow гейта с
именем `Continuum Contract Gate` или задать переменную точным непустым `name:`
этого workflow. Иначе каждое решение о восстановлении владельцем — `NOOP`
(`Contract Gate evidence is missing on the PR HEAD`), и приостановленная задача
никогда не возобновляется.

```yaml
# .github/workflows/contract-gate.yml
name: Continuum Contract Gate
on:
  pull_request:

permissions:
  actions: write
  contents: read
  pull-requests: read
  statuses: write

jobs:
  validate:
    uses: kodmial/continuum/.github/workflows/continuum-validation.yml@main
    with:
      continuum_ref: main
      # Keep the gate's result distinct from the CI caller's
      # continuum/validation context so the two cannot overwrite each other.
      status_context: continuum/contract-gate
      # Fork and Dependabot pull requests receive a read-only GITHUB_TOKEN, so
      # they cannot publish a commit status or dispatch repair. Validation
      # still runs; those PRs are gated by the job check instead.
      publish_status: ${{ github.event_name == 'pull_request' && (github.event.pull_request.head.repo.fork || github.actor == 'dependabot[bot]') && 'false' || 'true' }}
      dispatch_repair: ${{ github.event_name == 'pull_request' && (github.event.pull_request.head.repo.fork || github.actor == 'dependabot[bot]') && 'false' || 'true' }}
```

Для workflow гейта с другим именем задайте переопределение явно:

```sh
gh variable set CONTINUUM_CONTRACT_GATE_WORKFLOW_NAME --body "My Contract Gate"
```

## Необязательные цели диспетчеризации CodeRabbit

Контроллеры CodeRabbit и reconciler auto-merge запускают соседние workflows по
имени файла. Каждую цель можно переопределить для потребителя, чей
диспетчеризуемый входной workflow использует другое имя файла; пустой вход или
переменная сохраняют устаревшее имя Continuum, поэтому существующие установки не
меняются. Это простые имена файлов, а не пути: движки отвергают значение,
содержащее `/`, `\` или `..`, либо не заканчивающееся на `.yml`, и возвращаются
к устаревшему имени.

| Переменная репозитория | По умолчанию | Значение |
| --- | --- | --- |
| `CONTINUUM_CODERABBIT_RETRY_WORKFLOW` | `continuum-coderabbit-retry.yml` | Workflow, запускаемый, когда текущему HEAD всё ещё нужно ревью CodeRabbit. |
| `CONTINUUM_CODERABBIT_UNRESOLVED_WORKFLOW` | `continuum-coderabbit-unresolved.yml` | Workflow, запускаемый для сверки вердикта CodeRabbit по неразрешённым тредам. |
| `CONTINUUM_AUTO_MERGE_WORKFLOW` | `continuum-auto-merge.yml` | Workflow, запускаемый для сверки auto-merge после успешного запуска CI. |

Входы переиспользуемого workflow `coderabbit_retry_workflow`,
`coderabbit_unresolved_workflow` и `auto_merge_workflow` принимают те же
значения. Установленные вызыватели передают их пустыми, поэтому переменная
репозитория остаётся источником истины.

## Необязательный провайдер ревью PR-Agent

PR-Agent — необязательный стек ревью, выбираемый
`CONTINUUM_REVIEW_PROVIDER=pr-agent` и опирающийся на локальный для раннера мост
OpenCode. Выбор провайдера не использует устаревшие переключатели true/false.
Потребители, выбирающие `coderabbit`, сохраняют стек CodeRabbit; для PR-Agent
платный секрет провайдера не нужен. Архитектура и режимы сбоя описаны во
внутреннем документе `docs/pr-agent-opencode.md` (на английском).

| Переменная репозитория | По умолчанию | Значение |
| --- | --- | --- |
| `PR_AGENT_API_BASE` | `http://127.0.0.1:<bridge_port>/v1` | База OpenAI-совместимого бэкенда, с которым говорит PR-Agent. |
| `PR_AGENT_MODEL` | `openai/continuum-review` | Идентификатор маршрутизации LiteLLM (префикс `openai/` выбирает путь моста). |
| `PR_AGENT_MAX_TOKENS` | `128000` | Ограничение контекста пользовательской модели для бюджетирования промпта PR-Agent. |
| `OPENCODE_MODEL` | `opencode/muse-spark-1.3-contributor-free` | Модель OpenCode, используемая мостом PR-Agent. |
| `PR_AGENT_BRIDGE_PORT` | `18000` | Loopback-порт моста совместимости. |
| `PR_AGENT_OPENCODE_PORT` | `4096` | Loopback-порт `opencode serve`. |
| `PR_AGENT_VERSION` | `0.46.0` | Закреплённый релиз `pr-agent`, устанавливаемый на раннер. |
| `AUTOMATION_PR_AGENT_TIMEOUT_MINUTES` | `60` | Таймаут задачи PR-Agent. |

Модель инференции — тот же механизм `OPENCODE_MODEL`, который описывает раздел
выполнения агента (по умолчанию — бесплатный анонимный маршрут).

## Необязательные контроллеры

Render и квалификация Docker остаются общими конвертами выполнения. Их
принадлежащие потребителю команды/файлы уже являются хуками/входами; никакой
продуктовый репозиторий не предполагается.

Потребители Render предоставляют `RENDER_API_KEY` и явно настраивают свои
принадлежащие потребителю хуки. Continuum намеренно не поставляет значений по
умолчанию для путей репозитория:

| Переменная репозитория | По умолчанию | Значение |
| --- | --- | --- |
| `RENDER_JOB_SCRIPT` | пусто | Принадлежащий потребителю скрипт, управляющий жизненным циклом Render. Обязателен для выполнения Render. |
| `RENDER_CLEANUP_SCRIPT` | пусто | Принадлежащий потребителю скрипт, удаляющий эфемерный сервис Render. Обязателен для выполнения Render. |
| `RENDER_QUALIFICATION_SCRIPT` | пусто | Принадлежащий потребителю скрипт квалификации/классификации. Обязателен только для запусков с меткой квалификации. |
| `RENDER_CAPACITY_WORKFLOW` | пусто | Выделенный workflow решения об оптимизации/профиле/ёмкости, пробуждаемый для сбоев класса ёмкости. Пусто безопасно сохраняет источник. |

Те же значения можно передать входами переиспользуемого workflow `job_script`,
`cleanup_script`, `qualification_script` и `capacity_workflow`. Отсутствующий
обязательный хук завершается явным сбоем; ядро никогда не угадывает структуру
репозитория потребителя. Потребители квалификации Docker настраивают свой
репозиторий артефактов, имя бинарника, образ, лимиты памяти/прогонов и пути
результатов.

## Секреты

| Секрет | Когда требуется | Назначение |
| --- | --- | --- |
| `TAP_PAT` | Общим workflows нужны аутентифицированные записи в GitHub | Классический PAT со scopes `repo` + `workflow`. Scope `workflow` позволяет веткам задач OpenCode включать изменения `.github/workflows/**`; публикация всё равно идёт через PR и никогда не пишет напрямую в `main`. |
| `RENDER_API_KEY` | Включено выполнение Render | Учётные данные Render API. |
| `CHILD_RUNTIME_TOKEN` | Прямой вызов переиспользуемого workflow родителя | Доступ к делегированному дочернему репозиторию; установленные parent-вызыватели передают настроенные учётные данные родителя. |
| `CHILD_RUNTIME_REPOSITORIES` | Только устаревшая конфигурация parent | Необязательный вход совместимости для связей дочерних репозиториев. |
| `CONTINUUM_VERIFICATION_ATTESTATION_KEY` | Необязательно; включает подписанные возобновляемые свидетельства проверки | Необязательный ключ HMAC-SHA256, используемый только движком проверки на раннере. Workflow держит значение в неэкспортируемой shell-переменной, записывает его через `python -m continuum.verification provision-key` в приватный файл вне рабочего дерева задачи и передаёт в каждый вызов проверки только `CONTINUUM_VERIFICATION_ATTESTATION_KEY_FILE`. Движок отвергает значение в своём окружении и удаляет файл после чтения. Если ключ не задан, возобновлённый запуск пересобирает базовую линию и заново разрешает контракт, а не доверяет аттестации. |

Необязательный профиль Swift не определяет **никаких секретов подписи или
релиза**. Учётные данные подписи/релиза продукта принадлежат потребителю.

Каждая установленная parent-заглушка выполнения заполняет `CHILD_RUNTIME_TOKEN`
из собственного `TAP_PAT` родителя; очистка только метаданных использует
`GITHUB_TOKEN` вызывателя и не получает дочерних учётных данных. Прямые
вызыватели переиспользуемого workflow могут предоставить `CHILD_RUNTIME_TOKEN`
сами.

## Пример нового репозитория

1. Установите `core` из Continuum `main`.
2. Добавьте один проектный `.github/workflows/ci.yml` с именем `CI`, который
   вызывает
   `kodmial/continuum/.github/workflows/continuum-validation.yml@main`.
3. Передайте специфичные для проекта семантики build/test/toolchain через входы
   валидации или переменные `CONTINUUM_*`; не правьте установленный вызыватель
   `continuum-*.yml`.
4. Настройте `TAP_PAT`, если жизненному циклу нужны аутентифицированные записи.
5. Задайте `CONTINUUM_RUNNER`, только если `ubuntu-latest` не подходит.
6. Устанавливайте `tech` только для необязательного технологического профиля, а
   `parent` — только для делегированного выполнения.
7. Повторный запуск той же установки должен быть идемпотентным: проектные
   workflows сохраняются, а управляемая установщиком топология вызывателей не
   меняется.

Ни один исходный путь потребителя, название продукта, релизный репозиторий или
секрет подписи не добавляется в Continuum.
