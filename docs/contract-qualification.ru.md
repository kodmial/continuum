# Квалификация контракта Continuum (kodmial/continuum#286)

[English](contract-qualification.md) | [Русский](contract-qualification.ru.md)

Один блокирующий слияние контракт квалификации с тремя слоями.
Детерминированные правила живут в `src/continuum/contract_qualification.py`;
исполняемый гейт — переиспользуемый workflow
`continuum-contract-qualification.yml` (отображается как проверка **Contract
qualification**); принуждение слияния живёт в обоих reconciler'ах слияния.

| Слой | Где выполняется | Что доказывает |
| --- | --- | --- |
| 1 — детерминированная регрессия | Каждый pull request Continuum | Точный HEAD PR проходит полный контрактный набор. |
| 2 — интеграция жизненного цикла | Каждый pull request Continuum | Резервирование, восстановление, дедупликация и слияние по exact-HEAD работают сквозным образом. |
| 3 — живой canary | Ограниченное расписание плюс ручной запуск | Реальное состояние задач/PR/запусков продвигается на текущем `main` или падает явно. |

## Слой 1 — детерминированный регрессионный гейт (каждый PR Continuum)

- Workflow `Contract qualification` делает checkout точного HEAD PR и запускает
  на нём полный набор CI/контракта Continuum: `scripts/test-continuum.rb`,
  набор Python-движка (`tests/`) и набор runtime делегации.
- Свидетельства гейта должны относиться к точному текущему HEAD PR. Запуск для
  любого другого SHA устарел и никогда не удовлетворяет гейт.
- Fail closed внутри репозитория `kodmial/continuum`: отсутствующие, устаревшие
  или красные свидетельства блокируют оба пути слияния Continuum (общий
  auto-merge и слияние PR-Agent). Репозитории потребителей/Children этот гейт не
  запускают; они сохраняют свои CI, упаковку и настроенные обязательные
  workflow-гейты.

## Слой 2 — квалификация интеграции жизненного цикла (изменения жизненного цикла)

Проверяет реальный путь конечного автомата сквозным образом:

`задача -> планировщик/допуск -> воркер -> PR реализации -> CI ->
ревью -> ремонт/повторное ревью при необходимости -> слияние -> сверка/закрытие
исходной задачи`

Проба явно проверяет:

- `automation:in-progress` подразумевает атрибутируемый живой запуск/PR/lease,
  а не мёртвую метку;
- устаревшие lease освобождаются/восстанавливаются без вмешательства человека;
- завершённые/упавшие/отменённые воркеры не могут оставить задачу в подвешенном
  состоянии;
- дублирующиеся пробуждения объединяются, а не дублируют работу;
- WAIT/backpressure отличим от ERROR;
- watchdog двигает застрявшую работу вперёд в пределах ограниченного бюджета, а
  иначе падает громко;
- свидетельства exact-HEAD требуются до слияния;
- и общий auto-merge, и слияние PR-Agent подчиняются одному контракту (оба
  обращаются к запуску `Contract qualification` по exact-HEAD непосредственно
  перед любым вызовом `pulls.merge`).

## Слой 3 — живой canary (по расписанию)

- Проектная запись `contract-qualification-canary.yml` в репозитории Continuum
  выполняется по ограниченному расписанию (`43 */6 * * *`) плюс
  `workflow_dispatch`. Она намеренно не устанавливается потребителям, потому что
  её регрессионный слой выполняет собственный тестовый набор Continuum.
- Canary выполняется в выделенной задаче переиспользуемого workflow, которая
  держит записи в задачи и actions для ограниченного восстановления; вызыватель
  квалификации pull request остаётся verify-only, чтобы недоверенный код PR
  никогда не разделял эти разрешения.
- Canary выводит свою стадию из реального состояния задач, запусков и pull
  request. Он никогда не сообщает о завершённом сквозном прохождении по
  сконструированным данным.
- Предыдущая реализация требовала задаваемую оператором переменную
  `CONTINUUM_CANARY_ISSUE` и поэтому падала до наблюдения в запуске
  [43497991808](https://github.com/kodmial/continuum/actions/runs/43497991808).
  Задача `qualify / Qualify` того запуска завершилась успешно, затем
  `canary / Live canary` упала в `Observe the live canary task` с
  `CONTINUUM_CANARY_ISSUE must name the live canary issue; refusing to report
  canary success without an observed task.` Захваченный сбой сохранён в
  `tests/fixtures/contract-canary/run-43497991808.json` и управляет
  регрессионным тестом отсутствующей конфигурации.
- `CONTINUUM_CANARY_ISSUE`, когда задана, всё ещё переопределяет обнаружение
  для существующих установок. Когда она не задана, запланированный dogfood
  canary обнаруживает одну принадлежащую репозиторию задачу в
  `kodmial/continuum` по её стабильному маркеру
  `<!-- continuum-contract-canary repo=kodmial/continuum task=canary-main -->` и
  метке `automation:ready`.
- Если принадлежащего canary нет, canary создаёт безобидную задачу, единственная
  разрешённая работа которой — обновление `docs/contract-canary-fixture.txt`.
  Остальную часть жизненного цикла ведут обычный планировщик, воркер OpenCode,
  CI, Contract qualification, защищённое слияние и сверка исходной задачи;
  canary никогда не открывает pull request и не пишет в `main`.
- Новая задача canary создаётся, только когда предыдущая окончательно завершена
  (закрыта через слитый PR со свидетельствами `CI` и `Contract qualification`
  по exact-HEAD плюс успешный запуск воркера OpenCode, чей id встроен в
  каноническую ветку реализации этого PR, чей собственный канонический заголовок
  `OpenCode issue #N`/429-recovery называет ту же задачу, а run-scoped квитанция
  публикации называет именно эту ветку, pull request и опубликованный head
  commit; более поздние коммиты ремонта или синхронизации main могут продвинуть
  этот head, только когда история коммитов PR доказывает, что это доверенная
  автоматизация) и истекло документированное семидневное окно с её создания.
  Запись о завершении включает id этого запуска воркера, и workflow загружает
  этот запуск напрямую по id, чтобы ограниченная глобальная страница запусков не
  могла его скрыть. Воркер загружает квитанцию публикации как артефакт workflow,
  только когда публикует PR задачи; canary скачивает её из привязанного запуска,
  поэтому успешный запуск, ничего не опубликовавший, нельзя переиспользовать.
  Реализованный вручную PR с одним закрывающим ключевым словом или чья
  единственная связь с воркером — совпадающий заголовок задачи или
  переиспользованный id запуска ветки, никогда не считается живым
  доказательством жизненного цикла. Делегированный заголовок parent/child
  никогда не привязывает локальную задачу canary. Завершённый canary внутри
  этого окна наблюдается и сообщается со своим возрастом вместо замены. Более
  старые завершённые canary остаются закрытой историей; конфликт владения — это
  только более одной *открытой* принадлежащей canary.
- Дублирующиеся, некорректные или misplaced маркеры, отсутствующие метки,
  недоверенные авторы, более одной открытой принадлежащей canary, неполная
  пагинация и каждый сбой чтения GitHub (403/404/429/422/5xx) завершаются
  fail-closed. Перечни задач и pull request полностью пагинируются; завершённый
  canary заново загружает запуски для точного HEAD своего PR, чтобы
  ограниченная глобальная страница запусков не могла скрыть свидетельства.
  Workflow никогда не создаёт дубликат из неопределённых метаданных.
  Запланированная запись также сериализует запуски canary, чтобы две доставки не
  гонялись за пустым перечнем. Неудачное прямое чтение привязанного запуска
  воркера или его квитанции публикации фатально, а не тихий откат к более
  раннему ограниченному перечню запусков.
- Bootstrap разрешён только в `kodmial/continuum`. Не используются API
  администрирования/настроек репозитория, новое разрешение PAT, новый секрет,
  запись потребителя или запись ребёнка.
- Проба canary проверяет прямой прогресс относительно ограниченных дедлайнов
  каждой стадии жизненного цикла (см. `CANARY_STAGE_DEADLINES`).
- Стадия, превысившая дедлайн, записывает точные id canary/задачи/PR/запуска и
  застрявшую стадию, запускает ограниченное автономное восстановление там, где
  это безопасно (`MAX_CANARY_RECOVERY_ATTEMPTS`), а иначе падает громко.
- Commit status равен `success` только после того, как реальная задача canary
  закрыта через слитый PR со свидетельствами CI/контракта по exact-HEAD и
  успешный запуск воркера OpenCode, чья каноническая идентичность привязана к
  задаче, чей id встроен в ветку реализации, а run-scoped квитанция публикации
  называет эту ветку, pull request и опубликованный head commit; любой более
  поздний коммит ремонта или синхронизации main должен быть доверенной
  автоматизацией в собственной истории коммитов PR. Живой жизненный цикл,
  который всё ещё продвигается, публикует `pending` с наблюдаемой стадией и
  возрастом; он не считается завершённым сквозным прохождением. Поэтому первый
  запуск после merge сообщает `bootstrapped`/`pending`; живым сквозным
  доказательством является только последующая записанная последовательность
  задача/PR/HEAD/merge/запуск.

### Ручной запуск и устаревший вход `mode`

`mode` остаётся публичным входом `workflow_call` у
`continuum-contract-qualification.yml` (`type: string`, `default: verify`,
допустимые значения `verify` и `canary`), чтобы существующие вызыватели, всё
ещё передающие `mode:`, не падали на валидации входов. `mode: verify` — путь
свидетельств PR. `mode: canary` дополнительно запускает read-only пробу
контракта дедлайнов canary (`evaluate_canary`), что является устаревшим
поведением этого входа.

Живой canary с правами записи намеренно *не* выполняется из этого workflow:
вызываемый workflow не может повысить `GITHUB_TOKEN` вызывателя, поэтому задача
canary с правами записи здесь заставила бы read-only вызывателя pull request
выдать записи в задачи/actions. Поэтому живой canary существует ровно в одном
месте — `continuum-contract-canary.yml` — и никогда не перереализуется здесь.

Ручной эквивалент `mode: canary` — проектный workflow `Contract qualification
canary` (`contract-qualification-canary.yml`): выбор **Run workflow** выполняет
задачу квалификации и задачу живого canary в одном запуске. Оба маршрута ведут
к одной реализации canary.

## Безопасность ветки main (серверная, обязательна)

> [!IMPORTANT]
> Код не может защитить `main` сам по себе. Без серверной защиты ветки человек
> или неправильно настроенный workflow всё равно может писать напрямую в `main`.

Настройте защиту ветки GitHub (ruleset) для `main` со всем перечисленным:

- требовать pull request перед слиянием; никаких прямых push;
- требовать прохождения status checks перед слиянием, включая как минимум
  проверки, публикуемые workflow `CI` (его задачу `Validate` и контекст статуса
  `continuum/validation`), и workflow `Contract qualification`. Скопируйте
  точные имена проверок из реального запуска pull request перед сохранением
  правила; никакой check run буквально не называется `CI`;
- требовать актуальности веток перед слиянием (чтобы свидетельства exact-HEAD,
  которые заново проверяют reconciler'ы слияния, были именно теми
  свидетельствами, которые проверялись при ревью);
- не выдавать разрешения на обход для обычной разработки. Обход, если он вообще
  существует, зарезервирован для документированного break-glass с ревью после
  merge и никогда для рутинных изменений;
- блокировать force push и удаление ветки.

С такой защитой Definition of Done выполняется:

- намеренно сломанное изменение жизненного цикла отклоняется до слияния
  (красные/устаревшие/отсутствующие свидетельства exact-HEAD блокируют оба пути
  слияния);
- намеренно застрявший сценарий `automation:in-progress` обнаруживается и
  восстанавливается или падает громко в квалификации;
- запланированный живой canary доказывает прямой прогресс на текущем `main`;
- каждый поддерживаемый путь слияния блокируется, когда свидетельства контракта
  отсутствуют/устарели/красные;
- ни один прямой коммит разработки не может достичь `main` вне защищённого пути
  PR.
