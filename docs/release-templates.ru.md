# Справочные шаблоны release-workflow (архивные, неактивные)

[English](release-templates.md) | [Русский](release-templates.ru.md)

> [!WARNING]
> **Статус: ARCHIVED / HISTORICAL / INACTIVE / UNQUALIFIED (архив, история,
> неактивно, не квалифицировано).**
>
> Всё на этой странице описывает справочный материал в
> [`examples/release-templates/`](../examples/release-templates/). Это не
> поддерживаемая возможность релиза, не набор установщика и не доказательство,
> что релиз выполнялся на текущем main. Ничто здесь не добавляет активный
> триггер релиза, учётные данные публикации или миграцию потребителя. Работа над
> production-релизом и cutover остаётся отложенной.

Текущий поддерживаемый контракт Continuum — плоскость управления «задача → PR»,
описанная в [README](../README.ru.md). Автоматизация релиза сегодня не входит в
этот поддерживаемый контракт. Эта страница существует, чтобы будущая реализация
могла начать с исторического дизайна, а не восстанавливать его по памяти или
копировать специфичную для приложения автоматизацию одного потребителя.

## Что было восстановлено

Примеры восстановлены из одного исторического коммита:

```text
kodmial/continuum@0bbf57dbb8834d0aaef2cfb83f08ead7da623985
```

Три примера workflow — копии своих исторических тел с добавленным сверху
заголовком ARCHIVED. Общий workflow сохраняет историческую логику задач без
изменений, но два блока комментариев в его теле отредактированы: описание
разделения привилегий теперь называет оставшийся разрыв доверия транзакции, и
добавлен абзац, описывающий этот разрыв. Тела примеров consumer hand-off и Bun —
неизменённые копии их исторических источников. Вызыватель macOS, конфигурация
цели, `Info.plist` и файл entitlements — новые нейтральные к продукту примеры,
построенные против исторической поверхности `workflow_call` и схемы
конфигурации. Ни один живой workflow, модуль движка, правило установщика или
репозиторий потребителя не изменён.

## Архитектура

Исторический дизайн разделял один релиз на стадии, которые можно аудировать и
останавливать независимо:

```text
release selection
  -> version (optional Release PR)
  -> exact source commit
  -> resolve the target matrix
  -> per-target build (no publishing credential)
  -> sign
  -> verify artifacts, checksums, and signing identity
  -> transaction: GitHub draft -> publish once
  -> optional downstream publishers (Homebrew / MacPorts)
```

Общий workflow в
[`generic-release-workflow.yml`](../examples/release-templates/generic-release-workflow.yml)
— слой оркестрации. Он только `workflow_call`: у него нет собственного триггера
события, поэтому workflow выбора потребителя решает, когда он запускается. Он
намеренно не является macOS-скриптом:

- **resolve** читает политику и записывает матрицу, которую разделяют все
  последующие задачи. Публикационного токена у него нет.
- **target** выполняется один раз на строку матрицы, собирает из закреплённого
  `source_sha` и записывает один фрагмент. Публикационного токена у него нет, и
  он не может сконструировать пункт назначения.
- **transaction** — единственная задача с токеном записи. Она объединяет все
  фрагменты, отказывается от неполного набора и публикует один раз за
  выбранным вызывателем `environment` (в примере используется `release`, чьи
  правила защиты — ответственность вызывателя).

Разделение привилегий уменьшает экспозицию, но само по себе не является
границей безопасности. Исходное дерево, которое собирается, — недоверенный
вход, поэтому задача target, выполняющая его, не получает публикационных
учётных данных и пункта назначения релиза. Архивный workflow по умолчанию даёт
`contents: read` и повышает до `contents: write` только задачу transaction.
Каждый секрет объявлен по имени, и каждый привязан к адаптеру, который его
читает.

Остаётся один разрыв, и он — часть причины, почему этот материал не
квалифицирован. Задача transaction также делает checkout `source_sha` и
запускает `PYTHONPATH=src python3 -m continuum.cli` из этого дерева с
`GITHUB_TOKEN` в окружении, установленным из `secrets.RELEASE_TOKEN`.
Изменённый CLI в исходном дереве поэтому может прочитать публикационные учётные
данные, так что вынос токена из задач target не создаёт границу сам по себе.
Будущий квалифицированный дизайн должен выполнять каждую задачу, держащую
`RELEASE_TOKEN`, из отдельно доверенного движка, например checkout Continuum,
закреплённого на проверенной ссылке, а не из исходного дерева релиза. Пока это
решение о распространении движка не реализовано и не квалифицировано,
разделение — лишь снижение экспозиции.

У исторического ядра релиза за этим workflow была такая цепочка стадий:

```text
eligibility -> version -> release-pr -> validation -> source
            -> build -> sign -> verify -> draft -> publish -> sync
```

`release-pr` был необязательным: репозиторий, выпускающий релизы из тега, не
имеет release pull request. Архивный workflow принимает `version` и `source_sha`
напрямую, поэтому сам не открывает Release PR; потребитель, которому он нужен,
должен убедиться, что версия уже находится на точном исходном коммите до
dispatch.

Идемпотентность была привязана к релизу, а не к запуску workflow. Поэтому второй
dispatch, повторный запуск или другой наблюдатель тегов не мог опубликовать ту
же версию дважды. Concurrency-группа транзакции намеренно была
`cancel-in-progress: false`, потому что отмена публикации на середине оставляет
черновик, который должна распознать следующая попытка.

## Четыре разных слоя

Исторический материал использует слово «release» для четырёх разных вещей.
Разделять их — главное, что сохраняют эти шаблоны.

| Слой | Чем владеет | Где живёт здесь |
| --- | --- | --- |
| Общая оркестрация | Выполнение выбранного релизного события, закрепление источника, сборка матрицы, изоляция токена, объединение фрагментов, публикация один раз | `generic-release-workflow.yml`, `consumer-release-handoff.yml` |
| Адаптер/цель macOS | Типизированная политика для продукта macOS: архитектуры, идентичность бандла, профиль подписи, пины проверки, объявленные форматы артефактов и публикаторы | `macos-target.continuum.yml`, с историческими `apple.py` и `config.py` как источником схемы |
| Специфичные для потребителя скрипты сборки | Как конкретный проект вызывает SwiftPM, собирает `.app` и упаковывает файлы | Не включены. Это собственность потребителя и намеренно здесь не изобретается |
| Нижестоящие публикаторы | Обновления Homebrew tap или дерева MacPorts после появления GitHub release | Объявлены только как `homebrew` / `macports` в политике цели. Реализация публикатора не включена |

Специфичный для потребителя скрипт сборки — не общий workflow. Нижестоящий
публикатор — не адаптер подписи. Политика цели — не Actions workflow.

## Исторический пример macOS

Пример цели описывает один продукт SwiftPM с прямой дистрибуцией:

- **Две архитектуры:** `arm64` и `x86_64` с `universal: false`. Политика
  объявляет два продукта на архитектуру, а не один объединённый universal
  binary; сборка потребителя должна их произвести, потому что исторический
  адаптер не собирал ни один из них.
- **Одна идентичность:** исполняемый файл `ExampleApp` и бандл `ExampleApp.app`
  используют один идентификатор-заглушку `com.example.app`. Исторический
  адаптер сначала подписывает бинарники, затем запечатывает бандл с той же
  идентичностью, идентификатором и entitlements. Другой идентификатор заставил
  бы macOS считать следующий релиз другим приложением.
- **Подпись:** `self-signed-stable`, исторический первоклассный профиль.
  Специально созданный сертификат импортируется в одноразовую связку ключей на
  одну задачу. План закрепляет точное общее имя сертификата и проверяет его
  после подписи. Это не Developer ID и не заявляет notarization.
- **Воспроизводимость:** `timestamp: false` по умолчанию. Безопасная метка
  времени ломает побайтово идентичные повторные запуски и делает
  недействительными контрольные суммы, уже записанные нижестоящим манифестом.
  Это осознанный выбор, а не упущение.
- **Fail-closed материал:** `allow_adhoc_fallback: false`. Отсутствующий
  сертификат проваливает релиз, а не тихо создаёт ad-hoc подпись без стабильной
  идентичности.
- **Hardened runtime:** `hardened_runtime: true`. Набор entitlements имеет смысл
  только при этом обещании.
- **Форматы артефактов:** `tar.gz` и `zip` объявлены в политике. Исторический
  адаптер Apple подписывал и проверял бинарники и бандлы; он не создавал архивы,
  disk images, установщики или пакеты за вас.
- **Публикаторы:** `homebrew` и `macports` — объявления. Адаптер Apple никогда
  не загружает в tap или дерево портов, и ни один публикатор не включён в эти
  примеры.
- **Версионирование:** общий workflow принимает явную `version` и точный
  40-символьный `source_sha`. Исторический план бандла проставляет
  `CFBundleVersion` и `CFBundleShortVersionString` из версии релиза до
  запечатывания. Событие push тега не проверяет отправленный тег в историческом
  потоке: workflow передаёт `tag`, но `cmd_transaction` не передаёт его в
  `load_event`, а `version_checks_for` выводит `v<version>` из матрицы, поэтому
  сравнение показывает только, что матрица согласна сама с собой. Квалификация
  требует независимой проверки тега, например чтения ref тега и сравнения с
  запрошенной версией вне этого пути кода. Диспетчеризованный релиз передаёт
  единственную версию и не имеет тега. Правила защиты выбранного окружения,
  которые должен настроить вызыватель, могут требовать одобрения человеком перед
  публикацией, но это возможный гейт, а не независимый источник версии или
  сравнение версий.

Исторические ключи `Info.plist` в примере — минимум, по которому
идентифицируется `.app`. Замените значения-заглушки, сохраните оба ключа версии
и держите идентификатор бандла стабильным между релизами. Об одном ограничении
стоит сказать прямо: исторический план Apple **не** читал настроенный путь
`app_bundle.info_plist`. Он проставлял оба ключа версии в собственный
`Contents/Info.plist` собранного бандла и затем запечатывал его. Поэтому
`macos/Info.plist` — иллюстративный источник бандла, а не путь, который
потребляет адаптер, и план разрешал `<binary>` и `<bundle>.app` в фиксированном
каталоге `.build/release/`, а не в настраиваемом выходном пути.

### Замена заглушек

Каждое значение ниже — заглушка, а не production-значение по умолчанию.

| Заглушка | Замените на | Ограничение |
| --- | --- | --- |
| `ExampleApp` | Имя вашего исполняемого файла/продукта | Одно имя файла, не путь |
| `ExampleApp.app` | Имя вашего бандла приложения | Должно заканчиваться на `.app` |
| `com.example.app` | Ваш reverse-DNS идентификатор бандла | Используйте один стабильный идентификатор для бинарника и бандла; его изменение меняет идентичность приложения |

| `0bbf57dbb8834d0aaef2cfb83f08ead7da623985` в `uses:` вызывателя | Проверенная ссылка Continuum **после** восстановления и квалификации движка и CLI | Не направляйте этот пример на текущий `main` и не называйте его рабочим |

## Честный охват платформ

Основной поддерживаемый сценарий исполняемого файла исторического адаптера
Apple — **macOS SwiftPM**. Следующее автоматически не квалифицировалось и не
становится квалифицированным из-за этих примеров:

- подпись Developer ID, notarization и распространение через Gatekeeper;
- распространение через App Store и комбинации `ios` / `xcode-archive`;
- установщики `pkg` или `dmg` и другая платформенная упаковка;
- создание архивов `tar.gz` или `zip`;
- публикация в Homebrew tap или дерево MacPorts;
- Android, JVM или общий не-Apple путь сборки как рабочий релиз.

Историческая таблица входных точек содержала строки Android, JVM и generic, и
именно против неё написана общая матрица как точка расширения. Но схема
конфигурации принимала только `adapter: apple`, а таблица исполняемых адаптеров
исторической цепочки релиза содержала только Android и JVM. Поэтому общий
workflow выражал многоплатформенную архитектуру, которая на том коммите не могла
завершить релиз Apple. Этот разрыв — часть причины, почему файлы архивные, а не
представлены как работающая возможность.

Пример Bun отдельный и необязательный. Он не должен становиться архитектурой по
умолчанию для будущей реализации релиза.

Его собственная экспозиция учётных данных — часть причины, почему он не
квалифицирован. Архивный workflow Bun объявляет `contents: write` на уровне
workflow, а его шаг `actions/checkout` не задаёт `persist-credentials: false`.
Поэтому checkout оставляет `github.token` — токен репозитория с правами записи —
в `.git/config` проверенного дерева. Следующие шаги запускают
`bun install --frozen-lockfile`, а затем скрипт сборки потребителя из того же
дерева, поэтому управляемый исходниками код на коммите релиза может прочитать
токен во время сборки. Поскольку эта же задача ещё и публикует, перенос шага
публикации в более позднюю точку задачи не помогает. Отключения сохранения
учётных данных checkout недостаточно: код сборки может писать в `GITHUB_PATH`,
чтобы более поздний шаг разрешил изменённый `gh` или другой инструмент, и может
оставить другое состояние, которое наследует шаг публикации. Будущий релиз Bun
должен выполнять публикацию в отдельной доверенной задаче на чистом раннере,
которая получает только проверенные артефакты, чтобы сборка никогда не
разделяла раннер или окружение с публикационными учётными данными.

## Чего не хватает текущему main

Настоящий релиз — не один YAML-файл. Эти зависимости сегодня отсутствуют или не
квалифицированы:

1. **Нет движка релиза.** На текущем main всё ещё есть схема *конфигурации*
   релиза в `src/continuum/config.py`, но нет пакета `src/continuum/release/`:
   нет контракта, конечного автомата, согласования версий, ядра релиза,
   происхождения, назначения GitHub, транзакции или плоскости релиза.
2. **Нет release CLI.** На текущем main нет `src/continuum/cli.py`, а значит нет
   команд `release resolve`, `release target`, `release transaction`,
   `release plan` или `release sign`. Архивный workflow вызывает
   `PYTHONPATH=src python3 -m continuum.cli` из проверенного исходного дерева.
3. **Нет активных release-workflows или поддержки установщика.** На текущем
   main нет `.github/workflows/release.yml` или `release-bun-binary.yml`, и у
   `install.sh` нет release-набора. Ничто в `examples/` не устанавливается.
4. **Нет проходимого адаптера релиза Apple.** Исторический модуль Apple был
   планом подписи/проверки. Таблица `CORE_ADAPTERS` цепочки релиза содержала
   только Android и JVM, поэтому цель Apple отклонялась на стадии target с
   сообщением «план есть, но адаптера релиза, который цепочка может пройти,
   нет». План не создаёт манифест; транзакции нечего было бы объединять.
5. **Нет реализации сборки или упаковки SwiftPM.** План Apple подписывает уже
   существующие продукты. Он не запускает `swift build`, не собирает `.app` из
   пакета, не создаёт архивы `tar.gz`/`zip` и не строит `pkg`/`dmg`.
6. **Нет пути Developer ID, notarization или App Store.** Схема называет
   `developer-id`, `app-store`, `ios` и `xcode-archive`, но исторический адаптер
   отвергал их как нереализованные. Поддержка в схеме — не реализация.
7. **Нет нижестоящего публикатора.** `homebrew` и `macports` здесь — значения
   конфигурации. Модули публикаторов существовали в другом месте исторического
   дерева, но они не квалифицировались против текущего main и не восстановлены
   этой задачей.
8. **Нет решения о распространении движка.** Архивный workflow делает checkout
   `source_sha` вызывателя и ожидает release CLI в `src/continuum` этого дерева.
   Текущие потребители Continuum устанавливают тонкие вызыватели и держат код
   движка в Continuum; они не вендорят `src/continuum`. Будущий дизайн должен
   решить, как отдельно доверенный закреплённый движок релиза попадает в задачу,
   прежде чем workflow сможет работать, потому что транзакция выполняется с
   `RELEASE_TOKEN` в области видимости.
9. **Нет текущих свидетельств квалификации.** Исторические тесты и историческая
   документация ядра релиза не являются живыми свидетельствами для текущего
   main. Они также не демонстрируют полный путь сборки, подписи, упаковки,
   черновика и публикации macOS.

## Предварительные условия для настоящей квалификации позже

Будущее изменение должно удовлетворить всё перечисленное, прежде чем какой-либо
пример можно будет назвать рабочим:

1. Восстановить или перереализовать движок релиза и CLI с точными контрактами
   стадий и идемпотентности, описанными в историческом
   `docs/release-core-contract.md`.
2. Добавить проходимый адаптер релиза Apple, который собирает продукт SwiftPM,
   собирает `.app`, подписывает и проверяет его, выдаёт манифесты с digest и
   свидетельствами подписи и может быть объединён транзакцией.
3. Решить и реализовать модель распространения движка для потребителя
   переиспользуемого workflow.
4. Добавить активные workflows и поддержку установщика только в проверенном
   изменении, с одноразовым репозиторием потребителя как целью, защищённым
   release-окружением и одноразовым тестовым сертификатом подписи. Не
   мигрируйте production-потребителя в том же шаге.
5. Квалифицировать изоляцию секретов и установить границу доверия подписи:
   задачи resolve и target не держат публикационного токена; только transaction
   держит его. Задача Apple target действительно запускает CLI исходного дерева
   с `CONTINUUM_APPLE_P12` и `CONTINUUM_APPLE_P12_PASSWORD` в окружении, поэтому
   изменённый исходник может прочитать ключ подписи и парольную фразу.
   Ограничение этих секретов строкой Apple не изолирует их от собираемого кода,
   и доверенный движок транзакции не защищает задачу target. Запускайте
   транзакцию из отдельно доверенного движка, а не из исходного дерева релиза,
   потому что исходный CLI выполняется с `RELEASE_TOKEN` в области видимости.
   Не раскрывайте материал подписи задаче, которая выполняет недоверенный
   исходник; требуется установленная граница доверия подписи, например отдельно
   доверенный движок или изолированный шаг подписи, получающий только проверенные
   артефакты, до квалификации.
6. Квалифицировать семантику сбоев и восстановления: неполные наборы фрагментов
   отклоняются, прерывание посреди публикации возобновляется или безопасно
   сообщается, а дублирующее событие не может опубликовать дважды.
7. Квалифицировать цепочку exact-head: выбор -> версия -> исходный коммит ->
   сборка -> подпись -> проверка -> черновик -> публикация, с контрольными
   суммами, независимой проверкой того, что отправленный тег репозитория
   соответствует выпущенной версии, и независимым ревью артефактов.
8. Рассматривать Developer ID, notarization, App Store, установщики и
   нижестоящие публикаторы как отдельную работу по квалификации. Не выводите их
   из проходящей самоподписанной сборки macOS.
9. Квалифицировать необязательный пример Bun отдельно, включая его экспозицию
   учётных данных: `contents: write` уровня workflow плюс сохранение учётных
   данных checkout по умолчанию оставляет `github.token` читаемым для
   управляемого исходниками кода, который запускают `bun install` и скрипт
   сборки потребителя. Отключения сохранения учётных данных в checkout
   недостаточно, потому что код сборки может писать в `GITHUB_PATH` и заставить
   более поздний шаг запустить изменённый инструмент. Публикация должна
   происходить в отдельной доверенной задаче на чистом раннере, получающей
   только проверенные артефакты, чтобы ни один шаг сборки не разделял раннер с
   публикационными учётными данными, прежде чем называть этот путь
   квалифицированным.

До этого корректный статус — **INACTIVE / HISTORICAL / UNQUALIFIED**.

## Границы безопасности

- Ни один файл здесь не находится в `.github/workflows/` или
  `.github/caller-stubs/`.
- Ни одно правило установщика, активный workflow, модуль движка, планировщик,
  ревью, слияние или репозиторий потребителя не изменены.
- Не добавлены активный триггер релиза, тег, загрузка, публикация или миграция
  потребителя. Ручной dispatch примера вызывателя инертен внутри `examples/`.
- В примерах нет значений учётных данных; есть только имена секретов и
  выражения.
- В примерах нет названия продукта первого потребителя, идентификатора бандла,
  имени бинарника, tap, имени порта или приватного пути. Историческая схема
  читалась только ради формы, и каждое значение примера — нейтральная заглушка.
- Не заявлена функциональность, которой не было в историческом источнике. Там,
  где источник был неполным, разрыв назван выше.
